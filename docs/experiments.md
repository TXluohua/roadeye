# 实验记录

> 所有数字都是本机实测（RTX 4060 Laptop 8 GB / ultralytics 8.4.199 / torch 2.14.1+cu130）。
> 数据源：HuggingFace `TamAko783/Unified_Road_Defect_Dataset`（RDD2022 合并版）
> 训练集 12,838 图 / 验证集 4,509 图 / 4 类 / 共 37,614 个框

## E1 · 基线训练

### 设置

| 项 | 值 |
|---|---|
| 模型 | yolo11n.pt（预训练） |
| epochs | 50 |
| batch | 16 |
| imgsz | 640 |
| 优化器 | auto（AdamW + lr0 0.01） |
| 增强 | degrees=0, flipud=0, fliplr=0.5, hsv_v=0.4, mosaic=1.0, close_mosaic=10 |
| seed | 42，deterministic=True |
| 耗时 | **125 分钟**（7504 s，约 150 s/轮） |

### 结果（best.pt on val 4,509 图）

| 类别 | 实例数 | P | R | mAP50 | mAP50-95 |
|---|---|---|---|---|---|
| Longitudinal Crack (D00) | 4,807 | 0.589 | 0.415 | 0.422 | **0.215** |
| Transverse Crack (D10) | 2,992 | 0.553 | 0.427 | 0.413 | 0.173 |
| Alligator Crack (D20) | 1,769 | 0.627 | 0.600 | **0.612** | **0.325** |
| Pothole (D40) | 1,902 | 0.512 | **0.221** | **0.228** | 0.100 |
| **all** | 11,470 | 0.570 | 0.416 | **0.418** | **0.203** |

推理速度：preprocess 0.2 ms / **inference 1.6 ms** / postprocess 1.6 ms（每张）

### 收敛性判断

```
epoch   train/box  val/box   mAP50   mAP50-95
   25      1.710     1.914   0.374    0.176
   40      1.608     1.914   0.409    0.198
   50      1.516     1.943   0.419    0.203   ← val/box 开始上升
```

**结论：第 40 轮起 val/box_loss 由 1.914 升到 1.943，而 train/box_loss 继续下降 → 开始过拟合，已收敛。**
后 25 轮 mAP50-95 只涨 +2.75 个点。**再加轮数无用。**

## E2 · 为什么 D40 这么差？（诊断）

### 方法

`diagnose.py`：在 val 上逐张推理，把每个 GT 框按**面积占图比例**分桶，
统计每个 (类别 × 尺寸桶) 的 recall（IoU≥0.5, conf≥0.25）。

### 结果（全量 4,509 图 / 11,471 框）

| 类别 | 极小 <0.3% | 小 0.3~1% | 中 1~3% | 大 >3% | 合计 |
|---|---|---|---|---|---|
| D00 | **6%** (67/1071) | 30% (337/1126) | 52% (721/1381) | 63% (774/1229) | 40% |
| D10 | **7%** (38/534) | 38% (378/988) | 54% (504/936) | 63% (339/534) | 42% |
| D20 | 0% (0/26) | 11% (14/126) | 30% (100/336) | **70%** (902/1281) | 57% |
| D40 | **11%** (96/890) | 27% (168/625) | 33% (89/269) | 42% (50/119) | **21%** |

```
极小目标平均 6%，大目标平均 60%  →  差 10 倍
```

### 根因

1. **尺寸效应是决定性的**（不是类别歧义）
2. **D40 有 47% 的样本属于「极小」桶**（890/1903），而 D20 只有 1.5%（26/1769）
3. D40 在其他桶并不差（中 33% / 大 42%），**差就差在那 890 个极小坑槽（11%）**
4. D20 龟裂好，是因为它成片——>3% 的大目标占 72%，recall 70%

### 补充：目标实际像素尺寸

| 类别 | 面积%中位 | 较长边中位 | 长宽比中位 | AR>5 占比 |
|---|---|---|---|---|
| D00 | 2.54% | 144 px | 2.6 | 26% |
| D10 | 2.07% | 178 px | **5.1** | **53%** |
| D20 | 9.40% | 229 px | 1.6 | 1% |
| D40 | **0.57%** | **63 px** | 1.6 | 1% |

按面积桶看长宽比：

| 面积桶 | 框数 | 长宽比中位 | 较长边 | 较短边 |
|---|---|---|---|---|
| <0.3% | 89 | 1.8 | 34 px | **18 px** |
| 0.3~1% | 284 | 2.7 | 72 px | 26 px |
| 1~3% | 500 | 3.1 | 129 px | 42 px |
| >3% | 676 | 3.2 | 305 px | 86 px |

**结论：「极小」桶是真的小目标（34×18 px），不是细长目标。D40 是小而规整的坑槽（63 px 长边、面积 0.57%）。**

## E3 · 分辨率与切片推理的四组对照 ★核心实验

### 方法

`slice_infer.py`，随机采样 1200 张 val 图（seed=42），四组配置对照：

| 模式 | 做法 |
|---|---|
| **A** | 整图推理 @ imgsz 640（基线） |
| **B** | 切片：裁 320×320 → 缩放到 640（**目标放大 2 倍**），跨片 NMS 合并 |
| **C** | 整图推理 @ imgsz 1024（直接提分辨率） |
| **D** | **整图结果 + 切片结果融合**（两份都跑，统一做按类 NMS） |

### 结果

| 模式 | 极小<0.3% | 小0.3~1% | 中1~3% | 大>3% | **合计 recall** | 每张耗时 |
|---|---|---|---|---|---|---|
| **A** 整图@640 | 6.3% (46/725) | 35% | 51% | 64.2% (555/865) | **38.0%** | **24 ms** |
| **B** 切片 320→640 | **19.6%** (142/725) | 40% | 41% | 54.5% (471/865) | 38.5% | 533 ms |
| **C** 整图@1024 | 9.4% (68/725) | 38% | 48% | 58.4% | 38.3% | 28 ms |
| **D** 融合 ★ | **20.1%** (146/725) | **44%** | **56%** | **70.1%** (606/865) | **47.3%** | 1065 ms |

### 三条结论

**① 单纯切片是零和博弈**

```
极小目标  6.3% → 19.6%   (+13.3 个点)  ← 切片让目标在 patch 里变大
大目标   64.2% → 54.5%   (−9.7 个点)   ← 大目标被切片切断
净收益 ≈ 0
```

**② 单纯提高 imgsz 无效（+3.1 点）**

原因：**源图只有 512×512 / 600×600 / 720×720，letterbox 到 1024 是上采样，插值不产生新信息。**
（这也是为什么基线 mAP50 只有 0.418 —— 数据在采集端就被降采样过了）

**③ 融合才让两边都赢（+9.3 个点）**

```
小目标 +13.8，大目标 +5.9，整体 38.0% → 47.3%
原因：之前是"切片结果替换整图结果"，改成"两份结果 NMS 合并"后，
      小目标由切片提供、大目标由整图兜底
```

### 代价与优化方向

```
24 ms → 1065 ms（44 倍），瓶颈：320 tile + 0.5 重叠 → 720px 图要切 16 块
① overlap 0.5 → 0.25        块数约腰斩
② tile 320 → 384            块数下降，放大倍数降到 1.67×
③ 两阶段：整图先跑，只对低置信/空区域切片
```

## E5 · 融合方案的参数扫描（精度 vs 延迟）★ 最终配置

### 方法

在 E3 的 D 模式基础上扫 `tile` 与 `overlap`，随机 500 张 val 图（seed=42）。
基线 A 在同一 500 张上为 **39.1% / 25 ms**。

### 结果

| 配置 | recall | 耗时/张 | 极小<0.3% | 大>3% | 相对基线 | 框/张 |
|---|---|---|---|---|---|---|
| **A** 整图@640（基线） | 39.1% | **25 ms** | 4.0% | 64.5% | — | 1.6 |
| D tile320 ov0.50 ¹ | 47.3% | 1065 ms | 20.1% | 70.1% | +8.2 | 15.9 |
| D tile320 ov0.25 | 46.8% | 172 ms | 13.5% | 69.0% | +7.7 | 10.7 |
| D tile384 ov0.25 | 46.6% | 127 ms | 15.1% | 68.2% | +7.5 | 8.2 |
| **D tile448 ov0.25 ★** | **47.1%** | **123 ms** | 16.3% | 67.6% | **+8.0** | 8.2 |
| D tile384 ov0.40 | **47.5%** | 203 ms | 17.9% | 67.3% | +8.4 | 11.1 |

¹ 该行来自 E3 的 1200 张采样，其余为 500 张，绝对值略有差异但趋势一致。

### 结论：`tile=448, overlap=0.25` 是最优权衡

```
精度      39.1% → 47.1%     （+8.0 个点）
延迟      25 ms → 123 ms    （4.9 倍）
极小目标  4.0%  → 16.3%     （4 倍）
帧率      约 8 fps —— 行车记录仪抽帧到 5 fps 就够用
```

**关键优化是 `overlap` 从 0.5 降到 0.25**：耗时降到 1/6，精度只掉 0.5 个点。
因为 0.5 重叠时一张 720×720 的图要切 16 块，0.25 只切 9 块。

### 可复现命令

```powershell
# 基线
python slice_infer.py --sample 500 --modes A

# 最终配置（融合）
python slice_infer.py --sample 500 --tile 448 --overlap 0.25 --modes D
```

## E4 · imgsz 1024 重训（不是只改推理）

### 设置

| 项 | 值 |
|---|---|
| 模型 | yolo11n.pt（预训练） |
| imgsz | **1024**（训练与推理都是 1024） |
| epochs | **25**（★ 注意：基线是 50，轮数不同，见下） |
| batch | 8（1024 下显存所限，640 时是 16） |
| workers | 2（1024 下必须降，8 会触发共享内存崩溃） |
| 训练耗时 | 约 5.3 分钟/轮 × 25 ≈ 2.2 小时 |

### 结果（best.pt on val 4,509 图）

| 类别 | P | R | mAP50 | mAP50-95 |
|---|---|---|---|---|
| Longitudinal Crack (D00) | 0.534 | 0.410 | 0.398 | 0.193 |
| Transverse Crack (D10) | 0.486 | 0.446 | 0.390 | 0.159 |
| Alligator Crack (D20) | 0.602 | 0.570 | 0.591 | 0.303 |
| Pothole (D40) | 0.513 | 0.220 | 0.227 | 0.100 |
| **all** | 0.534 | 0.411 | **0.402** | **0.189** |

推理速度：preprocess 0.4 ms / **inference 4.1 ms** / postprocess 2.4 ms（每张，1024 输入）

### ⚠️ 这个结果不能直接和基线比 —— 轮数不同

| | 基线（E1） | 1024 重训 |
|---|---|---|
| imgsz | 640 | 1024 |
| epochs | **50** | **25** |
| batch | 16 | 8 |
| mAP50 | 0.418 | 0.402 |
| mAP50-95 | 0.203 | 0.189 |

**表面上 1024 更差（−1.6 点），但这是不公平对比**：基线跑了 50 轮，1024 只跑了 25 轮。
而且 1024 的训练曲线到第 25 轮**仍在上升**，`train/box_loss` 从 2.11 单调降到 1.636，没有走平迹象。

### 同轮次对比（这才是公平口径）

| 轮次 | 640 基线 mAP50 | 1024 mAP50 | 差值 |
|---|---|---|---|
| ep 25 | 0.374 | **0.4015** | **+2.75 点** |
| ep 40 | 0.409 | 未跑到 | — |
| ep 50 | 0.419 | 未跑到 | — |

同轮次下 **1024 反而高 2.75 个点**，且 `train/box_loss` 更低（1.636 vs 1.710）。

### 阶段性结论

1. **1024 不是"无效"，而是"更贵且更慢"**：每轮约 5.3 分钟（640 约 2.5 分钟），
   25 轮就花了 2.2 小时。同样时间里 640 能跑 50 轮以上。
2. **在等轮次上 1024 占优（+2.75 点）**，但绝对水平仍未追上 50 轮的 640 基线。
3. **收益是否值得**：如果 1024 跑满 50 轮，按当前斜率外推大约能到 0.44~0.46，
   相比基线 0.418 约 +2~4 点，代价是 **2 倍训练时间 + 2 倍推理延迟**（4.1ms vs 1.6ms）。
4. 这与 E3-C 的结论一致：**单纯提高分辨率的天花板有限**，因为源图本身只有 512~720，
   letterbox 到 1024 是上采样。真正有效的是**融合切片（+8.0 点）**。

### 待办

- [ ] 1024 跑满 50 轮，拿到收敛后的公平对比（约再需 2.2 小时）
- [ ] 若 1024 确实只有 +2~4 点，则维持"融合切片"作为主方案，1024 仅作为可选精度档

## E8（部分）· 图像质量阈值标定

### 方法

`tools/calibrate_quality.py`，随机 1,200 张验证图（seed=42），
用当前 `configs/quality.yaml` 逐张评估，统计各指标分布与不达标率。
产物：`assets/results/quality_calib.json`

### 结果

| 指标 | P1 | P5 | P50 | P90 | P99 |
|---|---|---|---|---|---|
| sharpness | 39.2 | 78.9 | 1200.0 | 4644.1 | 12751.8 |
| brightness | 66.4 | 83.9 | 130.6 | 164.0 | 187.5 |
| overexposure | 0 | 0 | 0 | 0.1 | 0.40 |
| underexposure | 0 | 0 | 0 | 0.1 | 0.11 |
| contrast | 12.5 | 25.1 | 51.6 | 79.7 | 90.9 |

### 发现的错误：原阈值过严

**原 `overexposure_max = 0.05` 把 30.50% 的正常验证图判为「不可用」**，
其中过曝一项就误杀 27.08%。

原因：路面高光、白线、天空本身就是超白像素，
正常图 P90 的过曝占比就有 0.17，P99 达 0.40 —— 也就是说 5% 这个阈值
把**相当一部分正常图片**当成了异常。

### 修正与效果

| | 修正前 | 修正后 |
|---|---|---|
| overexposure_max | 0.05 | **0.20** |
| 判「不可用」比例 | **30.50%** | **10.83%** |
| 过曝误杀 | 27.08% | **7.17%** |
| 检出 level=0.30 中度过曝 | 77% | 60% |

取舍说明：阈值放宽必然牺牲一点检出率（77% → 60%），
但**误杀率从 30.5% 降到 10.8% 是更重要的收益** ——
前置过滤的失败模式是"静默丢弃可用样本"，比漏掉几张过曝图危害大得多。

### 仍未做（剩下的一半 E8）

上面的标定只回答了"阈值是否合理"，**没有回答"质量前置到底降低了多少误检"**。
要回答后者需要：对同一批图分别做「直接推理」与「先过滤再推理」，
对比误检数。这是 E8 的正式部分，待做。
