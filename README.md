# RoadEye · 基于行车记录仪的道路病害自动巡检

> **车照常开，记录仪自动拍，系统自动认出坑槽裂缝，出一份能派工的清单。**
>
> 核心主张：**人不新增任何动作** —— 车本来就在路上跑，系统挂在记录仪后面。

> 📄 要把本项目写进简历，看 [`简历素材_RoadEye.md`](简历素材_RoadEye.md)
> —— 里面是所有数字的出处、三种长度的写法、面试预判问答，
> 以及一份「当前不能声称什么」的清单。

---

## 1. 为什么做这个：人的动线没有被改变

```
【现在】
  巡检员开车上路 → 目视找病害 → 停车 → 下车拍照 → 回办公室填表 → 报给养护队
       ▲                                                              ▲
       └──────────── 3~5 个人，一条路一年只能巡 2~4 遍 ───────────────┘

【装上系统之后】
  环卫车/公交/养护车照常跑（司机本来就在开）→ 记录仪自动拍
                                        ↓
                        系统自动识别 + 连续帧去重 + 出清单
                                        ↓
                          1 个人在办公室看清单 → 派工修补
       ▲
       └── 司机的动作【一个字没改】，新增人力 = 0
```

**这是本项目成立的唯一理由。** 很多"AI+硬件"方案要求人额外做一步
（贴标靶、专门跑一趟、凑近拍），那样净节省就归零了 —— 本方案不要求。

### 用户与 ROI

| 项 | 内容 |
|---|---|
| **用户** | 市政 / 公路养护部门，或道路养护承包公司 |
| **岗位** | 道路巡检员（中型城市 3~5 人） |
| **现状痛点** | 开车目视 + 停车 + 下车拍照 + 回办公室填表；一条路一年只看 2~4 次；从发现坑槽到修补平均滞后 2~4 周 |
| **净节省** | 专门巡路的 4 人 → 1 人调度，省约 3×8 万 = **24 万/年** |
| **覆盖频率** | 一年 4 次 → **每天**（×90） |
| **系统成本** | 软件 10 万 + 记录仪 50 台×300 元 = 1.5 万 |
| **回本** | 约 **6 个月** |

## 2. 快速开始

```powershell
# 0) 装依赖
pip install ultralytics opencv-python pyyaml pillow numpy

# 1) 下载数据（约 2 GB，实测 2.4 MB/s ≈ 7 分钟）
#    ★ Windows 上必须加 --ssl-no-revoke，否则 schannel 会卡在证书吊销检查
#    ★ 必须直连 hf-mirror，走代理反而只有 19 KB/s
python getdata.py all

# 2) 解压 + 生成 data.yaml（会自动修掉上游 yaml 里的绝对路径）
python tools/extract.py

# 3) 训练前先体检（★ 别跳过）
python tools/probe.py --root data/raw/unified --dup-sample 3000 --out assets/results/probe.json

# 4) 训练（约 2 小时）
python train.py

# 5) 诊断瓶颈（哪一类为什么差）
python diagnose.py

# 6) 切片推理对照实验（本项目的核心实验）
python slice_infer.py --sample 500 --modes A,D
```

## 4. 核心实验结果

完整数据见 [`docs/experiments.md`](docs/experiments.md)。

### E1 · 基线（yolo11n, imgsz 640, 50 轮）

| 类别 | P | R | mAP50 | mAP50-95 |
|---|---|---|---|---|
| D00 纵向裂缝 | 0.589 | 0.415 | 0.422 | 0.215 |
| D10 横向裂缝 | 0.553 | 0.427 | 0.413 | 0.173 |
| **D20 龟裂** | 0.627 | 0.600 | **0.612** | **0.325** |
| **D40 坑槽** | 0.512 | **0.221** | **0.228** | 0.100 |
| **all** | 0.570 | 0.416 | **0.418** | **0.203** |

推理 1.6 ms/张。第 40 轮起 `val/box_loss` 由 1.914 升到 1.943 而 train 继续降 → **已过拟合，加轮无用**。

### E2 · 为什么 D40 只有 0.221？（诊断）

按 GT 框面积分桶统计 recall（IoU≥0.5, conf≥0.25，全量 4,509 图）：

| 类别 | 极小 <0.3% | 小 0.3~1% | 中 1~3% | 大 >3% |
|---|---|---|---|---|
| D00 | **6%** | 30% | 52% | 63% |
| D10 | **7%** | 38% | 54% | 63% |
| D20 | 0% | 11% | 30% | **70%** |
| D40 | **11%** | 27% | 33% | 42% |

```
极小目标平均 6%，大目标平均 60%  →  差 10 倍
```

**根因：不是类别歧义，是尺寸。** D40 有 **47% 的样本落在"极小"桶**，而 D20 只有 1.5%。
D40 在中/大桶并不差（33% / 42%），差就差在那 890 个极小坑槽。

### E3 + E5 · 四组推理方案对照 ★核心

| 模式 | 极小<0.3% | 小0.3~1% | 中1~3% | 大>3% | **合计 recall** | 耗时/张 |
|---|---|---|---|---|---|---|
| **A** 整图@640（基线） | 4.0% | 35% | 51% | 64.5% | **39.1%** | **25 ms** |
| **B** 切片 320→640 | 19.6% | 40% | 41% | 54.5% | 38.5% | 533 ms |
| **C** 整图@1024 | 9.4% | 38% | 48% | 58.4% | 38.3% | 28 ms |
| **D** 整图+切片**融合** ★ | **16.3%** | 44% | 56% | **67.6%** | **47.1%** | **123 ms** |

**三条结论：**

1. **单纯切片是零和博弈**：小目标 `4.0%→19.6%`（+15.6），大目标 `64.5%→54.5%`（−10.0），净收益 ≈ 0
2. **单纯提高 imgsz 无效**：`6.3%→9.4%`。原因是**源图只有 512~720 像素，letterbox 到 1024 是上采样，插值不产生新信息**
3. **融合才让两边都赢**：小目标 +12.3、大目标 +3.1，**整体 +8.0 个点**

> 差异的根源：之前的实现是"切片结果**替换**整图结果"，
> 改为"两份结果**按类 NMS 合并**"后，小目标由切片提供、大目标由整图兜底。
> **一个缺陷，两种方案，差 8 个点。**

**最终配置：`--tile 448 --overlap 0.25`**（47.1% / 123 ms / 8 fps）。
`overlap` 从 0.5 降到 0.25 是关键 —— 耗时降到 1/6，精度只掉 0.5 个点。

```
roadeye/
├── getdata.py              下载 + gzip 校验 + 坏包重下（不做续传：续传会写错位致损坏）
├── train.py                训练（读 configs/train.yaml，支持 CLI 覆盖）
├── diagnose.py             ★ 按尺寸分桶诊断"哪一类为什么差"
├── slice_infer.py          ★ 整图 / 切片 / 融合 四模式对照实验
├── make_results.py         ★ 把实验结论固化成 assets/results/*.json
├── app.py                  ★ 演示台后端（FastAPI 单文件）
├── index.html              ★ 演示台前端（单页无构建，5 个模块）
├── run.py                  一键启动：补 JSON → 补样例 → 起服务 → 开浏览器
├── configs/
│   ├── paths.yaml          全项目唯一写路径的地方
│   ├── train.yaml          训练超参（道路病害专用增强）

│   ├── quality.yaml        图像质量前置阈值
│   └── dedup.yaml          连续帧去重参数
├── tools/
│   ├── probe.py            数据集探查（8 段报告，训练前必跑）
│   ├── extract.py          解压 + 修正上游 data.yaml 的绝对路径
│   ├── make_samples.py     从验证集挑 m1/m4 演示样例
│   └── make_m5_samples.py  合成"车驶过"连续帧（真值已知）
```

### 演示台怎么跑

```bash
python run.py            # 自动补 JSON、补样例、起服务并开浏览器
python run.py --port 8010 --no-browser   # 换个端口 / 不起浏览器
```

五个模块各自顶部固定三行：**解决什么问题 / 怎么做的 / 数字结论**，
然后才是可点的现场验证。页面只读 `assets/results/*.json`，
不在请求里重跑重指标 —— 所以打开是瞬时的。

### 训练配置里几个不能改的值

| 参数 | 值 | 为什么 |
|---|---|---|
| `degrees` | **0.0** | 旋转增强会把横向裂缝转成纵向裂缝，**标签语义就错了** |
| `flipud` | **0.0** | 上下翻转对路面没有物理意义 |
| `fliplr` | 0.5 | 左右翻转可以 |
| `patience` | 15 | 必须 < epochs，否则早停永不触发 |

## 6. 局限与未验证

**已证明（离线、公开数据）**
- 公开数据上的检测精度（mAP50 0.418）与逐类分解
- 尺寸分桶的漏检规律（极小目标 6% vs 大目标 60%）
- 融合切片推理的增益（+8.0 点）与延迟代价（4.9 倍）
- 数据集质量（无越界/无缺失标注）

**未证明（需真实部署）**
- 真实车载视频的稳定性（抖动、雨刷、夜间、逆光）
- 长时间运行的漂移
- GPS 定位与病害点位去重的准确性
- 与养护派工系统的对接
- 本项目用的是被上游 **resize 到 512~720** 的数据，原始 RDD2022 分辨率更高，
  真实性能上限应该更好（但未验证）

## 7. 工程笔记（踩过的坑）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | Windows schannel 证书吊销检查 | 所有 https 报 `SSL handshake failed` / `CRYPT_E_REVOCATION_OFFLINE`，看着像"网络不通" | curl 加 `--ssl-no-revoke`，立刻全通 |
| 2 | 代理 TUN 模式抢路由 | 国内从 3.75 MB/s 掉到 0.01 MB/s | 关 TUN，只留系统代理 |
| 3 | 断点续传导致 gzip 损坏 | 字节数对但 `invalid block type` | 不做续传；下完立刻 tarfile 校验，坏则重下 |
| 4 | 上游 data.yaml 是作者本机绝对路径 | 训练报路径不存在 | `tools/extract.py` 重写 yaml（不写 `path`，交给 ultralytics 按 yaml 目录解析） |
| 5 | `images/{split}` 布局的标签目录解析 | probe 报"0 个标签"而磁盘上有 | 判断 `dir.parent.name == "images"` 而不是 `dir.name` |
| 6 | 取前 N 张做实验 | 前段全是大目标图（极小目标只占 3%），结果不可代表 | 随机采样 + 固定 seed |
| 7 | NTFS 文件被占用时目录大小不更新 | 误判"下载卡住" | 用 `cmd dir` 或在 curl 断开间隙读 |
| 8 | 前端用 `cls*10` 反推类别名 | index 3 显示成 `D30`，而真实是 `D40` | 类别名只从 `configs/split.yaml` 的 `short` 映射取，**不在任何地方做算术推导** |
| 9 | 演示台进程内缓存了结果 JSON | 重跑 `make_results.py` 后页面还是旧数字 | 缓存键改成 `(mtime, data)`，文件一变就失效 |

## 8. 演示台（app.py + index.html）

五个模块，每个顶部固定三行「解决什么问题 / 怎么做的 / 数字结论」，下面才是现场可点：

| 模块 | 现场能做什么 | 数字结论 |
|---|---|---|
| M1 病害检测 | 点一张验证图，实时框出 4 类病害 | mAP50 0.418 / mAP50-95 0.203 |
| M2 切片推理对比 | 同一张图并排跑「整图」/「全量融合」/「按需切片」 | 39.1% → 47.1%（+8.0，108ms）；按需 +5.5 @ 51ms |
| M3 尺度诊断 | 看 GT 按面积分桶后的 recall 分布 | 极小目标 6% vs 大目标 60% |
| M4 图像质量前置 | 上传图或注入模糊/过曝/噪声，看能否判定 | 过曝图 sharpness 合格也会被挡下 |
| M5 连续帧去重 | 上传 12 帧，看归并成几个点位 | 147 框 → 16 点位（9.19×），过滤后 11 = 真值 |
| M6 分辨率对比 | 同一张图并排跑「基线 640」vs「重训 1024」 | 等轮次 1024 高 2.75 点，但成本翻倍 |

### 多权重对比（M6）

`app.py` 里有一个权重注册表，每个权重自带**它训练时的 imgsz**：

```python
WEIGHTS = {
    "baseline":  {"imgsz": 640,  "epochs": 50, "path": runs/baseline/...},
    "imgsz1024": {"imgsz": 1024, "epochs": 25, "path": runs/imgsz1024/...},
}
```

**为什么 imgsz 要跟着权重走**：640 训练的模型拿 1024 推理会造成尺度分布偏移
（E3-C 实测只 +3.1 点，那还不是真实收益）。所以调用时按权重取 imgsz，不能写死。

相关接口：`GET /api/weights`、`POST /api/compare_weights`、
`POST /api/detect {"weights": "imgsz1024"}`。

> 模型按路径分别缓存（`core/detect.py` 的 `_models` 字典），
> 两个权重可同时常驻，切换不重复加载。

### 按需切片（E10）

全量融合要切 9 块，但**大部分块是空路面**。按需切片先跑整图，只对两类区域再切：

1. **低置信框**（`conf < 0.45`）—— 有嫌疑没把握
2. **空白网格**（2×2 大格里一个框都没有）—— 整图看不见 ≠ 没有

实测（随机 500 张，与 E5 同口径）：

| 模式 | recall | 耗时 | 平均切块 | 单位精度代价 |
|---|---|---|---|---|
| A 整图 | 39.1% | 29 ms | 0 | — |
| **E 按需切片** | **44.6%（+5.5）** | **51 ms** | **3.4 块** | **4.0 ms/点** |
| D 全量融合 | 47.1%（+8.0） | 108 ms | 9 块 | 9.9 ms/点 |

E 的单位精度代价只有 D 的 40%，但只拿到 D 的 69% 精度——
因为 2×2 网格粒度太粗，一块里只要有一个检测就整块不切。

```powershell
python slice_infer.py --sample 500 --modes A,E,D
python slice_infer.py --sample 500 --modes A,E --no-empty-fallback   # 只切低置信框
```

> ⚠️ 60 张快速验证时 E（63.6%）反而高于 D（62.7%），扩到 500 张后关系翻转。
> 小样本上的"更优"往往是噪声，详见 `docs/experiments.md` E10。

### M5 的做法与实测

判断"两帧里是同一个病害"用**双条件**，缺一不可：

1. 整帧 dHash 汉明距离 ≤ 8 —— 说明是同一段路（只判这个会把相邻的**不同**的坑误合并）
2. 框 IoU ≥ 0.3 且类别相同 —— 说明是同一个病害

12 帧（源图含 11 个真实病害）实测：

| conf | 原始框 | 归并点位 | 出现 ≥3 帧 | 出现 ≥6 帧 |
|---|---|---|---|---|
| 0.25 | 147 | 16 | 13 | **11** |
| 0.30 | 140 | 15 | 13 | **11** |
| 0.35 | 127 | 14 | 12 | **11** |
| 0.40 | 118 | 13 | 12 | **11** |
| 0.50 | 95 | 12 | 9 | 8 |

**结论**：16 个点位里有 5 个只出现 1~5 帧，是 `warpAffine` 边缘拉伸产生的假阳性。
按「出现帧数 ≥ 总帧数一半」过滤剩下 11 个，与真值完全一致；
且这个口径在 conf 0.25~0.40 全区间都稳定成立 —— 不是靠调参凑的。
conf 提到 0.50 才开始漏真病害。

> 早先我把过滤口径定成「≥3 帧」，实测得 13 个，比真值多 2 个。
> 改成「≥半数帧」才对上 —— 真实病害本就是"每帧都看得见"的东西，
> 用它做阈值比拍一个固定数字更有依据。
